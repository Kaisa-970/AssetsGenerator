# 节点编辑器交互设计 v1

状态：部分实现；完整交互验收尚未完成。更新：2026-09-22。
当前能力见 [工作台状态表](../reports/node-editor-b2-status.md)，验证范围见
[预检与启动](../reports/node-editor-preflight-cpu-smoke.md)、
[继续提取与允许动作](../reports/node-editor-continuation-actions.md) 和
[结果比较](../reports/node-editor-output-comparison.md)。历史报告描述当时状态，不作为当前施工清单。
下文定义目标行为；实现状态以本节和状态表为准。

当前施工边界：
- 已实现结构化 QA、资产边界、人工决定独立展示和后端允许动作，不重复建设这些能力。
- 材质状态首片：逐输出展示 GLB 纹理引用、顶点颜色和已记录的后处理降级；无记录不推断原因，不将其等同于材质质量合格。
- 已接入执行预检、启动复核、继续提取、A/B 显式选用；继续提取目前限于可核验的文字分割联合 mask。
- 普通新运行已改成一次点击启动；子图及历史节点复用仍确认执行范围。
- 尚待收口：完整资产六步预算、真实模型改参数回放；跨运行人工决定确认首片已接入，真实人工组件复用验收待做。
- 远端服务可达性、GPU 资源不属于当前预检结论；模板绑定成功不能证明服务在线。

本文规定节点编辑器**面向人的行为**，不重复系统的内部契约。系统"是什么、对不对"由
design/ 下的契约文档定义；本文只回答：人看到什么、第一步点哪里、卡住时屏幕上出现什么、
以及哪些界面状态绝对不允许出现。

实现功能时以本文为准。本文与契约文档冲突时，契约文档定义正确性，本文定义呈现方式；
两者不可互相妥协的地方必须在实现前提出，不得自行取舍。

## 1. 这个界面为何存在

一句话：**通过可组合的节点处理现实观测，逐步做出资产，并且能方便地查看、调整和复用中间结果。**

完整资产是终点，不是唯一的中间目标。以下都是**正式任务**，不是例外，也不是"高级用法"：

- 试不同的提示词或分割配置，反复看分割结果；
- 选择、取反、合并对象，或只提取对象而暂不生成 3D；
- 复用已有结果，只调整下游节点；
- 用同一份输入并列比较两个模型或两套参数。

因此"能不能更清楚地看到中间结果并决定下一步"和"能不能走完主路径"同等重要。

### 1.1 服务谁

v1 只服务一个人：本机操作者，自己配好了模型环境，一次做一件事，串行使用 GPU。

不服务：多人协作、远程用户、无人值守批量任务、只看结果的评审者。

### 1.2 什么不该加

如果一个改动既不能让人更快拿到下一步的可用结果，也不能让人更清楚地知道系统验证了什么，
就不加。**注意这条不排斥探索性功能**：试参数、看中间结果、比较两个模型都属于"更快拿到
下一步"，它们是被鼓励的。它排斥的是与这两件事无关的通用平台能力（见第 9 节）。

## 2. 主路径与点击预算

已配置模型时，资产主路径定义为：**打开页面 → 看到可预览或下载的 GLB**。
无模型环境的首次体验走第 2.1 节的 CPU 图片路径，终点是图片，不要求生成 GLB。

| 步 | 用户动作 | 屏幕上必须出现 |
| --- | --- | --- |
| 1 | 打开本机地址 | 已配置的模板列表，以及每项"能不能跑"的结论 |
| 2 | 点一个模板 | 画布出现该模板的图，并显示编译结论 |
| 3 | 选输入来源并给图 | 图片缩略图 + 一句话说明"此时还没有执行任何模型" |
| 4 | 点「启动新运行」 | 运行面板出现，节点状态开始变化 |
| 5 | （人工节点时）点审查、确认 | 待办消失，下游继续 |
| 6 | 点输出 | GLB 预览或下载 |

主路径的显式操作上限是 6 步。**这条预算只约束"从零到一个资产"这条路径**，不约束
探索、调整和复用——第 3 节以明确入口和操作回放验收，不额外承诺固定点击次数。

主路径不得要求用户在第 3 步和第 4 步之间理解编译校验、输入契约和端口绑定。
这些必须**在主路径上被隐藏或给出默认值**，只在用户主动展开时出现。主路径上不允许
出现需要用户手填的 Artifact ID。

### 2.1 第一条体验路径必须不需要模型

新用户第一次打开，必须能完成一条不依赖任何模型环境的完整流程。`cpu-image-editor`
模板承担这个角色，本文把它确立为默认首屏推荐项，并规定它必须：不使用 GPU、
不加载任何权重，输出可预览和下载的图片。

CPU 验收路径为：打开页面 → 选 CPU 模板 → 上传图片 → 启动 → 预览或下载图片。
性能目标是在输入上传完成后，从启动到结果可预览不超过 30 秒；基准使用单张
1024×1024 RGB PNG、默认模板参数、本机磁盘且无其他重计算任务。验收记录必须注明
CPU、内存、存储、软件版本和实际耗时；该目标不作为任意硬件或任意输入的时限保证。

## 3. 三条必须写清的交互流程

本节是本文档最重要的部分。当前实现最绕的地方不是"能不能做"，而是**当前画布、所选历史
运行、正在预览的结果、下一次执行之间是什么关系**。以下三条流程把这个关系定死。

通用原则：**画布是意图，运行是事实。** 任何时刻界面上都要能回答"我看到的这个结果来自
哪次运行"，以及"我点执行会发生什么"。

### 3.1 流程一：分割满意后继续提取

场景：用户已经跑出满意分割，想在此基础上提取对象，不重跑分割。

```text
[当前画布]                      [所选运行]
 seed_image ──→ segment         run_A: seed_image → segment → (mask ✓)
                                    │
   用户满意，点「继续提取」          │
                                    ▼
   新运行 run_B, 复用 run_A 的 mask 输出作为输入
   只执行 extract 及其下游
```

必须明确的行为：

- **复用什么**：沿用原图与经后端核验的分割结果。涉及人工节点时，新运行只能提议
  复用旧决定；用户显式确认后，记录原决定引用及本次确认，不能默认继承。
  当前尚不支持的人工决定复用应明确提示，不能用普通计算节点复用替代。
- **执行什么**：按第 3.5 节进行后端预检。确认分割可复用后，界面才说明
  "只运行提取，不再运行分割"，并列出将执行和复用的节点。
- **保存什么**：产生**新运行**，不修改 `run_A`；`run_B` 的分割节点标记为"复用"而非"执行"。
- **不能做什么**：不能因为"结果一样"就悄悄直接接进 `run_A` 的后续节点。
  `run_A` 的历史不可改写。

### 3.2 流程二：修改提示词或参数

场景：用户改了某个节点的参数，已有结果不再对应当前配置。

必须明确的行为：

- **保留旧预览**，但**标记过期**：预览上出现明确标识，说明它来自旧配置。
- **列出受影响的下游**：说明哪些节点需要重新执行，哪些不受影响。
- **区分恢复与跨运行决定复用**：同一运行恢复且输入摘要、决定契约及证据校验通过时，
  保留原决定并显示"选择仍适用"；新运行即使候选相同，也必须显式确认复用旧决定。
  证据改变则显示"需要重新选择"。规则见
  [通用 DAG 编排设计第 10 节](../design/generic-dag-orchestration.md#10-人工节点)
  与[第 11 节](../design/generic-dag-orchestration.md#11-重试失效与复用边界)。
- **执行前必须重新编译**：图或参数改动后，旧编译结果作废。界面自动请求编译与预检，
  等待时说明"正在检查当前配置"，失败时给出原因；不额外要求用户手动点编译按钮。

### 3.3 流程三：比较两次结果

场景：用户用同一份输入跑了两套配置，想并列比较，并决定哪一份进入下游。

```text
 run_A: generate(TRELLIS.2) ─┐
                             ├─→ [预览: A | B]   选择其一 → 下游节点
 run_B: generate(TripoSR)  ─┘
```

必须明确的行为：

- **能切换查看**：两份结果都能打开，标题显示各自的 run ID 与节点。
- **明确当前选中项**：界面上始终显示"哪一份将作为下游输入"，不能只靠预览窗口的开关状态。
- **选择是一个显式动作**：绑定下游输入需要用户明确指定，不能是"最后预览的那个"。
- **不自动判定优劣**：系统不给出"哪个更好"的结论（见第 9 节的评分边界）。

### 3.4 三条流程共同的要求

- 每条流程都必须在界面上有一个**明确命名的入口**（如「继续提取」「重新执行受影响节点」
  「用作下游输入」），不能要求用户通过理解 DAG 语义来间接完成。
- 每条流程执行前，界面都要说明**将要执行什么、复用什么**。
- 涉及复用的操作产生**新运行**，旧运行保持不可变。

### 3.5 执行前预检与启动时复核

本节是目标行为。只读预检和启动时摘要复核已接入；检查范围仍有本文件开头列明的边界。

- 后端提供只读执行预检，按实际执行范围列出“将复用／将执行／受阻／待上游结果确认”
  及原因。“运行到这里”只检查目标及其祖先，无关分支不得阻挡。
- 预检必须使用已确定的输入引用、当前编译及绑定结果、来源运行快照，并检查复用所需的
  输入、参数、契约、实现、Backend 身份和证据完整性；前端配置比较只能作为提示。
- 未取得输入或上游尚未产生必要结果时，不承诺精确复用结果，显示待核验的节点及原因。
- 预检不启动模型、不领取任务、不恢复运行，也不修复缺失证据；成功结论绑定本次检查的
  输入、计划和来源快照。图、参数、输入或来源改变后，旧结论作废。
- 用户点击启动后，后端再次核验。若影响执行范围或复用结论的条件变化，停止创建或派发，
  返回新原因与新的执行说明，要求重新确认；不能默默把“复用”改成重新推理。
- 只有预检与启动时复核均支持时，才可承诺“不会再次调用分割模型”。

## 4. 四个维度必须独立显示

这是本界面的长期呈现规则。四维展示已实现，后续修改须保持其独立性。

编辑器必须**并列且互不覆盖**地显示四个维度，任何一个都不能被另一个取代：

| 维度 | 数据来源 | 用户读到的意思 |
| --- | --- | --- |
| 执行 | DAG 节点状态 | 这一步跑没跑、跑到哪 |
| QA | 具体 QualityReport 的 checks | 系统自动检查了什么、结果如何 |
| 人工决定 | 人工节点的 request/decision | 谁在什么时候选了哪个候选 |
| 资产边界 | scale_status、source、缺失检查 | 这个资产**没有**保证什么 |

### 4.1 已实现能力与后续验收

React 编辑器已提供结构化 QualityReport 汇总及逐项检查、资产边界和人工决定展示。
后续应验证实际资产的 `warn` / `fail` / `skipped` 及缺失记录呈现，
不要依据旧报告再次实现一个 QA 面板。已有组件和定向测试不等于全部资产场景验收完成。

### 4.2 独立性的具体含义

- 执行成功**不能**改变 QA 的显示。四个维度的取值各自独立渲染。
- QA 为 `warn` 时，执行仍然显示"成功"。不合并，不取最差值，不染成同一颜色。
- 人工决定**不是**质量信号。界面上不得出现"已通过审查"这类措辞。
- 资产边界在**没有记录**时必须显示"未评估"，不得显示为空白、不得显示为 `skipped`。

## 5. 状态词汇表

执行状态与 QA 状态使用后端已有取值，界面文案由本文固定，**不得在前端增造或推断
后端执行状态**。结果新鲜度与复用方式是独立维度，见第 5.4 节。

### 5.1 执行状态

| 后端取值 | 界面文案 | 颜色语义 |
| --- | --- | --- |
| `pending` | 待运行 | 灰 |
| `running` | 运行中 | 蓝 |
| `waiting_for_input` | 等待人工 | 琥珀 |
| `succeeded` | 完成 | 绿 |
| `failed` | 失败 | 红 |
| `interrupted` | 中断 | 红（与失败同色，但文案必须不同） |
| `blocked` | 上游未完成 | 灰 |
| `recovery_blocked` | 证据受阻 | 红（文案必须与失败、中断都不同） |

`failed` / `interrupted` / `recovery_blocked` 三者**不得合并成一个"失败"**，因为用户
动作不同：`failed` 要先核对原因及后端允许动作；`interrupted` 要先确认旧进程已退出；`recovery_blocked`
**要先看清是哪一类证据问题，再决定重试还是修复**。

### 5.2 允许的操作按阻塞原因区分

不能对 `recovery_blocked` 统一禁止或统一允许操作。`retry()` 在核验输入与远端状态后
可能支持重试这类节点。产品目标是由后端提供允许动作和拒绝原因，前端据此展示；
不能仅按状态或原因字符串自行授权。以下为建议引导，均以命令执行时的后端校验为准：

| 阻塞原因 | 界面动作 |
| --- | --- |
| 重试边界校验失败（`retry_input_invalid`） | 显示缺什么；修复后重试 |
| 上游证据损坏（`recovery_dependency_invalid`） | 先处理上游；可重试当前节点 |
| 输入与计划不一致（`recovery_input_mismatch`） | 说明差异；确认后重试 |
| 输出无法校验（`recovery_output_invalid`） | 可重试；持续失败则需人工核实 |
| 历史证据问题（`recovery_historical_evidence_invalid`） | 先看问题列表，再显式确认 |
| 子运行记录不一致（`recovery_child_invalid`） | 可重试 |
| 派发受阻（`dispatch_block_reason`） | 展示具体原因；若为进程状态未知，则在服务外核实，不提供强制继续 |
| 远端任务仍运行、提交结果未知或结果尚未核实 | 显示后端拒绝原因；按允许动作核实或恢复原任务，不提供强制重提 |

“可点击重试”只表示可以提交一次显式重试请求，不保证后端允许重新执行。
远端状态未知等情况不一定出现在 `dispatch_block_reason`，也可能由远端重试校验拒绝。
允许动作尚未得到后端确认时，显示“操作资格待核实”，不能承诺可重新推理。
所有实际重试仍经过后端输入、证据及进程/远端状态检查；拒绝后展示返回原因，
界面不得提供绕过检查的强制继续按钮。

### 5.3 质量检查状态

直接使用 QualityReport 的取值，**不得改写**：`pass` / `warn` / `fail` / `skipped`。
`skipped` 必须显示为"未评估"或"未执行该项检查"，**绝不能显示为"通过"**。

### 5.4 结果新鲜度与复用方式

这些标签与执行状态独立显示，不改写运行事实：

- “历史结果”：展示某次运行已经产生的结果，并标明来源运行和节点。
- “配置已变化／结果过期”：该预览不再对应当前草稿；不把原运行的“完成”改成“失败”。
- “待核验”：尚不能确认当前输入、配置和证据是否满足复用条件。
- “可复用”：后端预检通过，并标明核验范围；启动前仍需复核。
- “已复用”：新运行证据明确记录了复用来源；不能仅凭前端勾选状态显示。

前端比较可提示配置变化，但只有后端证据才能确认可复用、已复用和人工决定仍适用。

## 6. 绝不允许出现的界面状态

这一节是把仓库已经守住的立场变成可检查的清单。每一条都是硬约束。

1. **执行成功后不得出现任何形如"质量合格"的表述。** 执行完成只说明流程走完。
2. **`skipped` 不得显示为通过。** 没有相机注册就没有 render-back，这不是通过。
3. **`relative` 尺度的资产不得显示成"有尺寸"。** 必须显示"相对尺度，未标定为米制"。
4. **人工决定不得显示为质量结论。** 只显示"谁、何时、选了哪个候选"。
5. **无记录不得显示为空白。** 显示"未评估"。
6. **不得按目录时间或最新文件猜测运行成功。** 无法核实的证据就显示无法核实。
7. **不得把恢复说成"模型重放"。** 恢复已有输出和重新推理是两件事，文案必须区分。
8. **不得让用户手动复制 Artifact ID 来完成主路径。** ID 输入可以作为高级入口保留，
   但不能是唯一路径。
9. **浏览器状态不得影响服务端运行。** 刷新、关闭页面、清空缓存都不能改变运行的真相，
   也不能额外触发执行。
10. **不得因为界面方便而降低证据校验。** 预览失败就显示失败，不做"尽力而为"的读取。

## 7. 失败与恢复的用户视角

用户看到的是**一句话 + 一个后端允许的动作**。以下为常见映射，操作均受第 5.2 节约束。

| 用户看到 | 什么时候 | 一个动作 | 不能说的话 |
| --- | --- | --- | --- |
| 模型服务不可用 | `backend_unavailable` | 检查服务配置后重试 | 不要说"模型加载失败"（可能是配置错） |
| 模型执行超时 | `backend_timeout` | 确认显存/输入后显式重试 | 不要自动重试 |
| 模型执行失败 | `backend_failed` | 查看日志后显式重试 | 不要归因到输入（原因未知） |
| 输出校验失败 | `output_invalid` | 重试该节点 | 不要说成"模型质量差" |
| 发布失败 | `release_failed` | 检查磁盘与目录权限后重试 | 说"生成已完成，发布失败"，不要说"生成失败" |
| 契约不符 | `contract_error` | 检查该节点的绑定与参数 | 不要说"系统错误" |
| 证据受阻 | `recovery_blocked` | 按第 5.2 节的原因给动作 | 不要统一说"重试不能解决" |
| 执行中断 | `interrupted` | 确认旧进程已退出，再重试 | 不要说"已取消" |
| 有推理进程可能仍在运行 | 派发受阻 | 在服务外处理该进程 | **不要提供"强制继续"** |

最后两条最重要：**系统的默认是对不确定的进程状态说不**，这个立场必须在界面上体现为
"没有强制继续按钮"，而不是被一个方便的按钮绕过。

`release_failed` 要特别说清：生成与 QA 已经完成，失败的是发布动作，整体运行仍记为失败。
不要把它显示成"生成失败"，那会让人误以为要重跑模型。

### 7.1 恢复与刷新的用户动作

恢复必须是**显式**的。刷新页面、重新打开运行都只读状态，不自动执行。
界面上必须有一句明确的话说明这一点，当前实现里的"查看状态不执行任务"就是这个意思，
应当保持并在所有恢复入口保持一致措辞。

刷新后显示的是**服务端最新状态**，可能与刷新前不同（后台任务已经推进）。这不属于
不一致，属于正确。要求的是刷新本身不触发任何执行。

## 8. 降级路径

用户当前处在哪一级必须一眼可见。三级：

| 级别 | 条件 | 能做什么 | 界面必须说明 |
| --- | --- | --- | --- |
| CPU | 没配任何模型 profile | 导入、编码、缩放、mask 合成等 CPU 节点 | "未配置模型，可运行 CPU 模板" |
| 本地模型 | 配了本地 profile 并通过身份校验 | 单图生成、多视图重建 | 显示加载了哪些 profile、是否通过校验 |
| 远程服务 | 配了 HTTP/ComfyUI 服务 | 远程推理 | 显示远程服务是否可达、是否已验证 |

关键约束：**模板列表里每一项都要标注它属于哪一级、当前环境能否运行。**
不能运行的模板要么不显示，要么显示且明确标注原因。

当前实现里"仅契约 · 未配置实现"是一个好的起点，应扩展到整个模板列表。

## 9. 明确不做

以下内容在 v1 范围内**不做**，新增时需要先改本文件：

- 节点分组、折叠、可封装复用的子图节点（“运行到这里”的依赖子图裁剪已在范围内）
- **自动**布局（手动拖动节点与保存布局**已在范围内**，是当前画布的核心能力）
- 批量与队列
- 多用户、账号、权限
- 云端或跨机器调度
- 通知系统
- 移动端
- 通用质量评分、能力认证、资产打分
- 任意 Python 命令、任意路径读取、模型安装

自由连线**已在范围内**（它是当前实现的核心能力），但主路径不得依赖它。

## 10. 落地顺序

以下是原定实施顺序，不是尚未完成的任务清单；当前剩余项见文档开头。

**线一：让人看清结果质量**

1. **补上结构化 QA 展示。** 将现有 QualityReport 链接扩展为汇总与逐项检查，独立于执行状态显示。
2. **补上资产边界。** scale_status、source、缺失检查的汇总，无记录显示"未评估"。
3. **按原因区分阻塞动作。** 已由后端提供允许动作；持续按第 5.2 节校验拒绝原因和状态过期边界。

**线二：让人少重跑、能接下游**

4. **先实现只读执行预检，再完成第 3 节的明确入口。** 优先“继续提取”，随后是
   “比较两次结果”。已有复用机制不等于预检、人工决定确认及全部交互已完成。
5. **缩短主路径。** 把手填 Artifact ID 从主路径移出，给默认值或自动填充。
6. **模板列表标注降级级别。** 与线一第 2 项共用同一份"未评估"措辞。

线一第 1、2 项修复的历史缺口现已完成实现；仍须保留第 11 节的验收要求。

## 11. 验收

分三层，不能互相替代。**截图只能证明第一层。**

**第一层 · 界面截图：信息是否清楚。**
- 一个 `warn` 的资产，用户能否在执行成功的同时看到它为什么 warn？
- 一个 `skipped` 的检查，界面上会不会出现"通过"字样？
- 一个 `relative` 尺度的资产，用户能否看出它没有真实尺寸？
- 没有模型环境时，CPU 图片路径及其图片输出终点是否清楚？

**第二层 · 操作回放：任务是否顺畅。**
- 已配置模型时，资产主路径能否在 6 步内从打开走到 GLB，且不需要手填任何 ID？
- 无模型时，能否完成 CPU 图片路径，并按第 2.1 节记录性能条件与耗时？
- 修改参数后，旧预览是否标记过期，同时保留原运行的完成状态？
- 第 3 节的每条流程，用户能否在界面上找到明确命名的入口，一次走通？
- 刷新页面后显示的是服务端最新状态，且刷新本身没有触发任何执行？

**第三层 · 运行记录：执行、复用和来源是否正确。**
- "继续提取"后，分割节点在运行记录中标记为复用，且 SAM 调用次数没有增加？
- "比较两次结果"后，下游节点实际绑定的是用户指定的那一份，而不是最后预览的那一份？
- 重试获准后，旧的失败 attempt 是否保留？再次被拒绝时是否显示最新阻塞原因？
- 预检通过后若输入、配置或证据变化，启动是否停止并要求重新确认，而非偷偷重跑模型？
- 新运行复用人工决定时，是否有原决定引用与用户显式确认；同一运行恢复是否保留有效决定？
- 远端提交状态未知时，即使没有 `dispatch_block_reason`，界面是否仍遵守后端的重试拒绝？

本文档本身不构成任何上述功能已实现的证据。
